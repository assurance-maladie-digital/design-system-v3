# Nouvelle prop `validateOn` sur les champs

Tous les composants de champ de formulaire à l'exeption des dates pickers acceptent une nouvelle prop `validateOn` qui détermine le déclencheur de la validation Vuetify : `blur`, `input`, `submit`, `invalid-input`, combinables avec les modificateurs `lazy` et `eager` (ex. `eager blur`).

Elle ne s'applique qu'en mode Vuetify (`useVuetifyValidation`) et **remplace `isValidateOnBlur`** si les deux sont fournies. En mode Synapse, elle est ignorée et un warning est émis en développement.

Cas particulier de `SyTextArea` : le composant déclarait déjà `validateOn` (avec `eager input` par défaut), mais ne l'appliquait pas. Les valeurs de `validate-on` explicitement définies sont désormais prises en compte ; avec `eager`, les erreurs peuvent s'afficher dès le chargement.

## Conduite à tenir

- Pour choisir quand la validation se déclenche en mode Vuetify, utilisez `validate-on` ; il remplace `is-validate-on-blur` si les deux sont fournis.
- Vérifiez les valeurs de `validate-on` existantes sur `SyTextArea` et adaptez-les si nécessaire, car elles influencent désormais le déclenchement de la validation.
- En mode Synapse, continuez d'utiliser `isValidateOnBlur` : `validateOn` n'y a aucun effet.

# SyTextField — prop `direction` supprimée

La prop `direction` de `SyTextField` n'a jamais eu d'effet : `VTextField` ne la prend pas en charge, et la valeur finissait en attribut HTML invalide `direction="horizontal"` sur l'`<input>` (RGAA 8.2, code source valide). La prop est supprimée : elle n'est plus déclarée dans les props, les types (`SyTextFieldProps`) ni la documentation. Tous les composants construits sur `SyTextField` sont concernés (`PhoneField`, `NirField`, `PasswordField`, `DatePicker`, etc.).

Le rendu ne change pas. Un `direction="…"` encore passé à `SyTextField` est ignoré : il n'est pas transmis à l'`<input>`.

## Conduite à tenir

- Retirez `direction` de vos usages de `SyTextField`. Si vos templates sont vérifiés en mode strict (`strictTemplates`), ou si vous construisez les props en TypeScript à partir de `SyTextFieldProps`, la propriété `direction` y est désormais signalée comme inconnue.
- Si vos tests ou snapshots attendaient l'attribut `direction` sur l'`<input>`, mettez-les à jour.

# Nouveau point d'entrée `@cnamts/synapse/vuetifyOptions` — ajout au contrat

Un nouveau point d'entrée exporte `createVuetifyOptions`. La fonction renvoie la configuration Vuetify de Synapse (thèmes, `defaults`, locale, icônes) sans enregistrer les composants ni les directives Vuetify.

`createVuetifyInstance` (`@cnamts/synapse/vuetifyConfig`) ne change pas : elle est désormais construite sur `createVuetifyOptions` et enregistre toujours tous les composants et directives.

Cet ajout n'est pas cassant.

## Conduite à tenir

C'est désormais la configuration recommandée : `vite-plugin-vuetify` (import automatique des composants) et `createVuetifyOptions`. La documentation ne présente plus qu'elle, dans la section « Configurer Vuetify » de la page *Guide Du Dev / Démarrage / Installation*, qui remplace la page *createVuetifyInstance*.

```ts
import { createVuetify } from 'vuetify'
import { createVuetifyOptions } from '@cnamts/synapse/vuetifyOptions'

export const vuetify = createVuetify(createVuetifyOptions())
```

Les composants Vuetify inutilisés ne sont alors plus inclus dans votre bundle.

`createVuetifyInstance` reste disponible et fonctionne comme avant : vous pouvez la garder.

# PeriodField — règles de validation ciblées par borne

Nouvelles props `customFromRules` / `customToRules`, ainsi que `customFromWarningRules` / `customToWarningRules` : les règles passées dans ces props ne s'appliquent qu'à la date de début ou de fin, ce qui permet d'afficher des messages différents pour chaque borne.

`customRules` et `customWarningRules` restent inchangés : leurs règles continuent de s'appliquer aux deux bornes. L'option `fieldIdentifier` d'une règle sert à rattacher le message au champ visé, elle ne restreint pas la portée de la règle.

## Conduite à tenir

- Si vous utilisiez `fieldIdentifier` dans `customRules` / `customWarningRules` pour cibler une seule borne, la règle s'appliquait en réalité aux deux : déplacez-la vers `customFromRules` / `customToRules` (ou `customFromWarningRules` / `customToWarningRules`) et retirez `fieldIdentifier`.

# SyTextField — contraste du texte d'aide, du préfixe, du suffixe et du libellé flottant (changement visuel)

Plusieurs textes de `SyTextField` étaient affichés avec l'opacité « medium emphasis » de Vuetify (60 %) et n'atteignaient pas le contraste de 4,5:1 exigé pour un texte de moins de 24 px (RGAA 3.2, WCAG 1.4.3), même sur fond blanc :

- texte d'aide (`helpText`), sous le champ ou à la place du message : 4,24:1 sur blanc, 3,99:1 sur `#e7ecf5` ;
- préfixe et suffixe (`prefix`, `suffix`), à l'état neutre et en erreur : 4,24:1 sur blanc ;
- libellé flottant d'un champ rempli à l'état neutre (valeur initiale, champ réinitialisé, etc.) : 2,80:1 sur blanc.

Ces textes sont désormais affichés sans opacité réduite :

- texte d'aide, préfixe et suffixe en couleur `on-surface` du thème ;
- libellé flottant en couleur de bordure du thème (`#545859` pour les thèmes CNAM, PA et AmeliPro), soit 7,2:1 sur blanc.

L'API ne change pas. En dehors du préfixe et du suffixe d'un champ en erreur, les états erreur, avertissement, succès et désactivé ne changent pas. Tous les composants construits sur `SyTextField` sont concernés (`PhoneField`, `NirField`, `PasswordField`, `DatePicker`, etc.).

Le libellé affiché à l'intérieur d'un champ vide ne change pas (5,74:1 sur blanc, conforme).

## Conduite à tenir

- Si vos tests visuels capturent un `SyTextField` avec un texte d'aide, un préfixe, un suffixe ou un champ rempli à l'état neutre, mettez à jour vos baselines.
- Si vous surchargiez ces couleurs pour corriger le contraste, vous pouvez retirer ces surcharges.

# SyTable / SyServerTable — pied de tableau vide retiré du DOM

Le slot `bottom` contenait toujours un conteneur `div.d-flex.align-center.pa-2`, même sans contenu à afficher. Ce conteneur vide laissait une bande blanche de 16 px sous le tableau (#2736). Il n'est plus rendu que s'il contient la gestion des colonnes (`enableColumnControls`) ou la pagination.

Il disparaît donc dans ces cas, quand `enableColumnControls` est désactivé :

- `hideDefaultFooter` est activé ;
- le tableau n'a aucune ligne (état vide) ;
- `SyServerTable` est en cours de chargement et `items` n'est pas encore défini.

Les props, événements et slots ne changent pas.

## Conduite à tenir

- Si vos tests ou snapshots attendaient ce conteneur vide sous le tableau, mettez-les à jour.

# SyTable / SyPagination — nouvelles props et pagination en boutons

## Nouvelles props publiques

| Composant | Prop | Type | Valeur par défaut | Utilisation |
|---|---|---|---|---|
| `SyTable` | `hideCaption` | `boolean` | `false` | Masque visuellement la légende `caption`, tout en la conservant pour les lecteurs d’écran et le nom de la pagination. |
| `SyPagination` | `buttonMode` | `boolean` | `false` | Utilise des boutons pour changer les données affichées. Avec `ariaControls`, chaque bouton référence la zone mise à jour. Les points de suspension sont des `span` non interactifs. |

Ces props sont optionnelles. Pour masquer une légende sans perdre son nom accessible :

```vue
<SyTable
  suffix="contacts"
  :headers="headers"
  :items="items"
  caption="Liste des contacts"
  hide-caption
/>
```

Avec plusieurs tableaux, renseigner une légende différente pour chacun. Le nom de la pagination reprend `caption` ; sans légende, il reste « Navigation de pagination ».

## Changement du HTML de pagination de SyTable

`SyTable` active désormais le mode boutons pour sa pagination : les actions passent de liens `<a href="#">` à des `<button type="button">`. Les boutons référencent les résultats via `aria-controls` et les pages numériques ont des noms accessibles comme « Page 2 ».

`SyPagination` utilisé seul conserve les liens par défaut. Il faut activer `buttonMode` pour utiliser les boutons. L’alignement de `SyServerTable` sera traité dans une autre PR.

## Annonces de statut

La zone de statut de `SyTable` annonce uniquement les changements : compteur de sélection, page et plage de résultats, filtres ou tri. Elle ne lit plus la liste des numéros de lignes sélectionnées ni l’état complet à chaque interaction.

## Conduite à tenir

- Adapter les tests E2E qui ciblent les liens de pagination de `SyTable` (`a[href]`, `getByRole('link')`) pour cibler les boutons et leurs noms accessibles, par exemple `getByRole('button', { name: 'Page 2', exact: true })`.
- Adapter les surcharges CSS `.sy-pagination a` si elles doivent aussi s’appliquer aux boutons : utiliser `.sy-pagination button` ou cibler les deux éléments lorsque le style est partagé avec une pagination en liens.
- Garder une `caption` descriptive, même avec `hideCaption`, et des légendes distinctes lorsque plusieurs tableaux sont présents.
