		<CriteriaSection>
			<CriteriaCard title="Structure sémantique">
				<ul>
					<li><strong>Champ</strong> : <code>&lt;input&gt;</code> readonly (texte) sans <code>role="combobox"</code> forcé ; l’ouverture se fait via clic ou clavier.</li>
					<li>
						<strong>Attributs ARIA de l’input (aria-expanded / aria-haspopup)</strong> : ces attributs sont volontairement retirés pour les raisons suivantes :
						<ul>
							<li><em>Incompatibilité avec le rôle natif</em> : un <code>&lt;input type="text"&gt;</code> possède le rôle implicite <code>textbox</code>. Selon le W3C/WAI-ARIA, l’usage de <code>aria-expanded</code> et <code>aria-haspopup</code> sur ce rôle est invalide et lève des erreurs critiques lors des audits (axe, Tanaguru).</li>
							<li><em>Rejet du rôle combobox</em> : forcer un <code>role="combobox"</code> sur l’input rendrait les attributs valides, mais serait sémantiquement inexact. Notre champ est en <code>readonly</code> et ouvre un véritable panneau de dialogue complexe (calendrier), pas une simple liste d’options de saisie.</li>
							<li><em>Alternative robuste</em> : l’accessibilité de l’ouverture est garantie contextuellement. L’ouverture du calendrier déplace immédiatement le focus dans une modale avec un <em>focus trap</em>. Le lecteur d’écran comprend le changement de contexte et l’annonce via les régions <code>aria-live</code>, rendant l’expérience fluide et conforme aux standards.</li>
						</ul>
					</li>
					<li><strong>Panneau</strong> : calendrier exposé dans un vrai <code>dialog</code> modal, contenant la grille de jours et ses contrôles.</li>
					<li><strong>Relations</strong> : <code>aria-controls</code> relie l’enveloppe activatrice du champ readonly au <code>dialog</code> lorsqu’il est ouvert ; le <code>dialog</code> est nommé par un titre stable « Calendrier » via <code>aria-labelledby</code> ; <code>aria-owns/expanded/haspopup</code> ne sont pas surchargés sur l’input natif.</li>
					<li><strong>États</strong> : <code>aria-disabled</code> / <code>aria-readonly</code> alignés sur les props, messages d’erreur/avertissement/succès annoncés via la zone de messages du champ.</li>
				</ul>
			</CriteriaCard>

			<CriteriaCard title="Ouverture, fermeture et focus">
				<ul>
					<li><strong>Ouverture clavier</strong> : <kbd>Entrée</kbd> ou <kbd>Espace</kbd> sur le champ ouvre le calendrier ; l’icône déclenche l’ouverture avec la souris.</li>
					<li><strong>Fermeture</strong> : <kbd>Échap</kbd> ferme et valide ; un clic extérieur ferme aussi le panneau ; le focus est ensuite rendu au champ.</li>
					<li><strong>Piège de focus</strong> : <kbd>Tab</kbd>/<kbd>Shift+Tab</kbd> restent dans le panneau ouvert (boutons d’entête, grille de jours, bouton « Aujourd’hui »).</li>
				</ul>
			</CriteriaCard>

			<CriteriaCard title="Messages et annonces">
				<ul>
					<li><strong>Live region</strong> : le mois/année affichés sont annoncés via une unique région de statut dédiée, pour éviter les annonces en double.</li>
					<li><strong>Statuts</strong> : erreurs/avertissements/succès sous le champ ; le bouton « Aujourd’hui » a un <code>title</code> explicite.</li>
					<li><strong>Guidage</strong> : placeholder et libellé (ou <code>aria-label</code>) décrivent l’action attendue.</li>
				</ul>
			</CriteriaCard>
		</CriteriaSection>

		<BestPracticesSection>
			<ul>
				<li>Fournir un <code>label</code> explicite ; utiliser <code>placeholder</code> uniquement comme aide complémentaire, jamais comme seul libellé.</li>
				<li>Garder un <code>label</code> court et distinct (ex. « Date de naissance »), sans y répéter le format : en mode calendrier seul, l’utilisateur ne saisit pas ; le format attendu n’a pas à être annoncé. <code>helpText</code> reste utile pour une précision métier ou pour indiquer que le champ ouvre un calendrier.</li>
				<li>Le champ activateur avertit nativement l’utilisateur de l’affichage du calendrier (« Activation ouvre un calendrier » via <code>aria-describedby</code>, annonce désactivée quand le champ est <code>disabled</code>) : cette information n’est annoncée qu’aux technologies d’assistance ; l’indiquer dans le <code>helpText</code> la rend visible pour tous.</li>
				<li>Conserver <code>format</code> et le texte d’aide cohérents avec la valeur attendue ; utiliser <code>helpText</code> pour expliquer le format métier (préférer <code>helpText</code> à <code>hint</code> : il reste visible en cas d’erreur).</li>
				<li>Laisser <code>isValidateOnBlur</code> à <code>true</code> si les erreurs ne doivent apparaître qu’après la sortie du champ ; réserver <code>validateOnSubmit()</code> à la soumission.</li>
				<li>En lecture seule, le champ n’est pas éditable et le calendrier ne doit pas être proposé ; pour un champ sélectionnable mais non saisissable, utiliser le mode calendrier normal, pas <code>readonly</code>.</li>
				<li>En plage de dates, préciser l’ordre attendu dans le <code>helpText</code> et laisser la séparatrice visible.</li>
				<li>Vérifier la cohérence des bornes <code>period</code> pour ne pas masquer les jours attendus.</li>
				<li>Ne pas ajouter <code>role="combobox"</code> au mode calendrier seul : ce mode ne permet pas la saisie d’une valeur.</li>
				<li>Éviter les champs désactivés : même lorsque son contraste est conforme (critère RGAA 3.2), un champ désactivé via la prop <code>disabled</code> crée une charge mentale. Préférer un champ actif accompagné d’un message expliquant la contrainte, ou indiquer visiblement pourquoi le champ est indisponible et comment l’activer.</li>
			</ul>
		</BestPracticesSection>
